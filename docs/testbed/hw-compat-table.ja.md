## 分類の定義

| 分類 | 意味 |
|---|---|
| **そのまま実機化可** | 攻撃・観測の経路がプロトコル／ロジック層にあり、Renode の輸送路（TCPソケット、CAN hub）を実機の等価物（シリアルブリッジ、実CANバス、USB-CAN）に置き換えるだけで、演習の前提・判定条件がそのまま成立する |
| **注入方法の変更が必要** | 学習目標と判定条件は実機でも維持できるが、攻撃者の「位置」そのものが Renode ホスト側の仕掛け（ホスト内プロキシ、クロスリンク注入器、2衛星構成）に依存しており、実機では別の装置・構成でその位置を再現する必要がある |
| **実機対象外（Renode専用）** | 前提がエミュレーション固有の性質に依存し、実機では演習として成立しない |

## 全体に共通する Renode → 実機の置き換え（全演習共通の前提）

分類以前に、全演習で次の置き換えが必要になる。これらは演習ごとの表では繰り返さない。

1. **CAN hub → 実CANバス**: Renode の `canHub` は理想的なハブで、衝突・ACK・バスオフ・終端の影響がない。実機では CAN classic 1 Mbps（全アプリ共通 `CAN_BITRATE 1000000`、`firmware/apps/*/src/main.c`）、終端は幹線両端のみ（ロードマップ決定）。攻撃者ノード／USB-CAN は **ACK を返す通常モード**でなければならない（silent/listen-only では送信フレームが ACK エラーで再送され続け、演習の前提が崩れる。ロードマップ フェーズ3の「ACK 可能な通常モード」と同旨）。
2. **TcpCanInjector → 実注入装置**: 攻撃者がバスにいる演習の注入器は、CPU を持たない Renode 専用 C# ペリフェラル（`attacker/TcpCanInjector.cs`、TCP に `"<hex can id> <hex data>"` を書くとフレームが出る）。実機では USB-CAN アダプタ（SocketCAN 等）か、攻撃者用の5枚目のノード基板に置き換える。
3. **スペースリンク TCPソケット → シリアルブリッジ**: COMM の `usart2`（PA2/PA3、115200 bps）が Renode では ServerSocketTerminal。実機では Pi/PC 上の地上局ソフト（既存 Python GS）を USB-UART ブリッジ経由で USART2 に接続する。このブリッジが、リンク系演習の「傍受・記録」の観測点も兼ねる。
4. **コンソール FileBackend → 実UARTコンソール**: 各ノードの `usart3` コンソール出力（ファイル）が、多くの演習の成功判定（例: `EPS: COMM rail OFF`）の根拠。実機ではノードごとに USB-UART でコンソールを常時取得できることが必須要件。
5. **ホスト側 PowerDomain → 実電源スイッチ**: Renode には「電源の切れたマシン」の概念がないため、EPS のレール GPIO（PD5）をホストプロセス（`src/cuberange/renode/powerdomain.py`）が監視し、対象マシンを halt／ELF再ロードで再起動している。実機では EPS のレール出力が**実際に COMM ノードの電源を断つ**配線にすれば、この仕掛けは不要になり、むしろ実機の方が忠実になる（復帰時の RAM 初期化も実物どおりになる）。
6. **仮想時間 → 実時間**: Renode の実行プロファイル（quantum 2 ms、ci/interactive）で保証されていたタイミング再現性は実機では消える。タイムアウト・待ち時間ベースの判定（verify の待機、EPS の 30秒自動復帰 `FDIR_RESTORE_MS 30000` ※これはファームウェア内タイマなので実機でも同じ）は実時間で再確認が要る。
7. **vuln/hard ペアの切替え**: 全演習が `firmware-matrix.yml` のビルドフラグ1つの差で vuln/hard イメージを作り分ける方式。実機ではノードごとに SWD 等での再書込み（または2セットのイメージ切替え手段）が必要。演習後の初期状態復旧（ロードマップの設計要件: ノード別電源断、BOOT/NRST 外部制御、再書込み経路）は全演習共通のハードウェア要件。

## 特に注意すべき演習

1. **クロスリンク系4件（変更8件のうち4件: EX-X01 / EX-S01 / EX-S02 / EX-D01）**: v1 テストベッドの想定構成（共通ノード基板×4・単機）に存在しない要素が2つある — (a) COMM の **fdcan2** を実際に配線する第2 CAN バスとトランシーバ、(b) peer 衛星役の **COMM ノード1枚追加**（scenario 上 SAT1 は COMM のみでよい。フル2機＝8ノードは不要）。この4件をフェーズ1の対応表で「実機化する」と決めるなら、基板設計に fdcan2 トランシーバと peer 用5枚目を最初から含める必要がある。含めない場合、この4件は「後段フェーズ送り」が実質的な分類になる。
2. **中間者系4件（変更8件の残り4件: EX-D02 / EX-L02 / EX-L03 / EX-U01）**: 攻撃者の位置＝GS ブリッジそのもの。つまり**ブリッジは単なる USB-UART 変換ではなく、フレーム単位のドロップ／差替え／損失注入と、その完全なログを持つ「故障注入装置」として設計する必要がある**。これはフェーズ3（市販品での実機成立）のブリッジ選定・実装に直接影響する。特に EX-L02 は損失の再現性（seed 制御）が判定の前提で、自然のリンク損失では代替できない。
3. **EX-F02**: 本表の調査時点では24件で唯一 Renode でも未実行だったが、その後 PR #7 でマージされ、CI で Renode 実走が確認済み（verify 5テスト全て PASSED。過程で実欠陥1件――vuln イメージで public block が最適化により脱落――を発見・修正）。「そのまま実機化可」は実機側についての文書ベースの見込みであり、実測ではない。
4. **EX-D01 の FIFO ペーシング**: Renode モデルでは FDCAN RX FIFO 深さ3のため4フレーム注入に 50 ms 間隔が必要だった（設計書 W64 に実測記録）。実機の Zephyr FDCAN 設定で FIFO 深さが異なる可能性があり、注入条件が変わる／消える場合がある。**未確認**（リポジトリ内に実機 FIFO 設定の根拠なし）。
5. **EX-B01 / EX-L01 の電源復帰**: Renode の PowerDomain は ELF 再ロードで「クリーンな再起動」を保証している。実機では COMM ノードの電源再投入で RAM が初期化される（実物の挙動）ため問題は逆に小さいが、EPS の 30秒自動復帰（ファームウェアタイマ）と組み合わさった際の観測手順は実機で1回通し確認が要る。
6. **対象外が0件であること自体**: 全演習が「実機の同一ファームウェア＋実バス／実リンク」で再現可能な設計になっており、Renode 固有の物理（仮想 GPIO、ホスト halt 等）は全て実機の等価物に置換可能だった。これは CubeRange の設計方針（Renode はピンマルチプレクスすらモデルしないが、デバイスツリーは実機で動く形に書く、という crosslink.overlay の記述）の帰結と見られる。
