# The 24 exercises on the physical testbed

- Written: 2026-11-20 (a phase 1 specification-freeze preparation draft; a proposal before review, not a freeze decision)
- Scope: the 23 exercises on main (`exercises/`) plus EX-F02 on `feat/ex-f02` (read via `git show feat/ex-f02:...`, without checking the branch out)
- Assumptions (the phase 1 testbed roadmap): four common node boards (STM32H753; COMM/OBC/EPS/ADCS) plus a backplane (power, CAN classic trunk), EPS single-point power entry and distribution, no battery, CAN physically wired, the ground station bridged from a Pi or PC
- Basis: each exercise's README / scenario.resc / solve.py / mitigation.md and the firmware (`firmware/apps/*/src/main.c`, `firmware-matrix.yml`). Anything the documents do not establish is marked "unconfirmed" rather than filled in by guesswork.

## Classification

| Class | Meaning |
|---|---|
| **Runs on hardware as-is** | The attack and observation paths live at the protocol/logic layer; replacing Renode's transports (TCP sockets, the CAN hub) with their physical equivalents (a serial bridge, a real CAN bus, USB-CAN) leaves the exercise's premises and pass conditions intact |
| **Needs a different injection method** | The learning goal and pass conditions survive on hardware, but the attacker's *position* itself depends on a Renode host-side mechanism (a host proxy, a crosslink injector, a two-spacecraft setup) that must be recreated by a different device or configuration |
| **Out of scope for hardware (Renode only)** | The premise depends on a property of the emulation itself, and the exercise does not stand up on physical hardware |

## Replacements common to all exercises (Renode to hardware)

Before classification, every exercise needs these replacements. They are not repeated per exercise in the table.

1. **CAN hub to a real CAN bus**: Renode's `canHub` is an ideal hub — no collisions, ACK effects, bus-off, or termination effects. On hardware it is CAN classic at 1 Mbps (the common `CAN_BITRATE 1000000` in `firmware/apps/*/src/main.c`), terminated at the trunk ends only (roadmap decision). An attacker node or USB-CAN adapter must run in a normal, acknowledging mode: in silent/listen-only mode its frames are never ACKed and are retransmitted forever, which breaks the exercises' premises (the same point as phase 3's "a normal mode that can ACK").
2. **TcpCanInjector to a physical injector**: the injector for exercises where the attacker sits on the bus is a Renode-only C# peripheral with no CPU (`attacker/TcpCanInjector.cs`; writing `"<hex can id> <hex data>"` to a TCP socket emits a frame). On hardware it becomes a USB-CAN adapter (SocketCAN or similar) or a fifth, attacker node board.
3. **Space-link TCP socket to a serial bridge**: COMM's `usart2` (PA2/PA3, 115200 bps) is a ServerSocketTerminal under Renode. On hardware the existing Python ground station connects to USART2 through a USB-UART bridge from the Pi/PC. That bridge is also the observation point (intercept and record) for the link exercises.
4. **Console FileBackend to a real UART console**: each node's `usart3` console output (a file) is the evidence for many pass conditions (for example `EPS: COMM rail OFF`). On hardware, capturing every node's console continuously over USB-UART is a hard requirement.
5. **Host-side PowerDomain to a real power switch**: Renode has no notion of a powered-down machine, so a host process (`src/cuberange/renode/powerdomain.py`) watches the EPS rail GPIO (PD5) and halts / reloads the target machine's ELF. On hardware, if the EPS rail output actually cuts the COMM node's power, the mechanism is unnecessary — and the hardware version is the more faithful one (RAM initialisation on return is the real behaviour too).
6. **Virtual time to real time**: the timing reproducibility Renode's execution profiles (quantum 2 ms, ci/interactive) provided disappears on hardware. Timeout- and wait-based judgements (verify waits; the EPS 30-second auto-restore `FDIR_RESTORE_MS 30000` is a firmware timer, so it behaves the same on hardware) must be re-confirmed in real time.
7. **Vuln/hard pair switching**: every exercise builds its vuln/hard pair from one build flag in `firmware-matrix.yml`. On hardware each node needs reflashing over SWD (or another way to switch between two image sets). Returning to the initial state after an exercise (the roadmap design requirement: per-node power cut, external BOOT/NRST control, a reflash path) is a hardware requirement common to all exercises.

## Points of attention

1. **The crosslink four (4 of the 8 changed: EX-X01 / EX-S01 / EX-S02 / EX-D01)**: two elements absent from the v1 testbed's assumed configuration (four common node boards, one spacecraft) — (a) a second CAN bus and transceiver actually wiring COMM's **fdcan2**, and (b) one added **COMM node as the peer** (on the scenario, SAT1 needs COMM only; a full second spacecraft of 8 nodes is not needed). If phase 1 decides these four are in scope for hardware, the board design must include the fdcan2 transceiver and the fifth, peer board from the start. If not, "deferred to a later phase" is their effective classification.
2. **The man-in-the-middle four (the other 4 of the 8: EX-D02 / EX-L02 / EX-L03 / EX-U01)**: the attacker's position *is* the GS bridge. That means **the bridge must be designed not as a mere USB-UART converter but as a fault-injection device**: frame-level drop / replacement / loss injection, with a complete log of what it did. This bears directly on the bridge choice and build in phase 3 (off-the-shelf bring-up). EX-L02 in particular makes loss reproducibility (seed control) a precondition of its judgement; natural link loss is not a substitute.
3. **EX-F02**: the only one of the 24 never run even on Renode ("Not yet run"). Before any hardware question, phase 0 (PR plus a CI run) must establish that it stands on Renode. Its "runs on hardware as-is" here is a document-based expectation, not a measurement.
4. **EX-D01's FIFO pacing**: in the Renode model the FDCAN RX FIFO is 3 deep, so injecting 4 frames needed 50 ms spacing (measured and recorded in design W64). The real part's Zephyr FDCAN configuration may have a different FIFO depth, in which case the injection conditions change or vanish. **Unconfirmed** (no basis for the real FIFO setting exists in this repository).
5. **Power return in EX-B01 / EX-L01**: Renode's PowerDomain guarantees a "clean restart" by reloading the ELF. On hardware, power-cycling the COMM node initialises RAM (the real behaviour), so the problem is smaller — but the observation procedure in combination with the EPS 30-second auto-restore (a firmware timer) wants one end-to-end confirmation on hardware.
6. **That the out-of-scope count is zero is itself a finding**: every exercise is designed to be reproducible with "the same firmware on real hardware plus a real bus / real link", and every Renode-specific piece of physics (virtual GPIOs, host halts) had a hardware equivalent. This appears to follow from CubeRange's design stance (Renode does not even model pin multiplexing, but the devicetree is written to run on real hardware — as the crosslink.overlay comment puts it).

| Feature | Required by | Notes |
|---|---|---|
| CAN classic 1 Mbps physical wiring plus termination (ends only; switching separated out as fault injection) | All exercises | The backplane trunk. The bit rate is a firmware constant |
