# EX-F02 の対策 — ダンプは、そのためのブロックからだけ返す

*English: [mitigation.md](mitigation.md)*

## 変更点

ビルドフラグ1個の背後に、検査を1つ。
すべてのビルドがパケットそのものに対して行う2つの検査（メモリ ID 0、1〜128オクテット）の後に置く。

```c
#if CUBERANGE_OBC_PUS6_ALLOWLIST
	if (!dump_allowed(address, length)) {
		printk("OBC: REJECTED PUS 6 dump of %u octets at 0x%08x "
		       "(public block is %u octets at 0x%08x)\n",
		       (unsigned int)length, (unsigned int)address,
		       (unsigned int)sizeof(obc_public_block),
		       (unsigned int)(uintptr_t)obc_public_block);
		return;
	}
#endif
	public_block_refresh();
	send_dump_report(source_id, mem_id, address, length);
```

検査そのもの:

```c
static bool dump_allowed(uint32_t address, uint16_t length)
{
	const uint64_t start = (uintptr_t)obc_public_block;

	return address >= start && (uint64_t)address - start + length <= sizeof(obc_public_block);
}
```

最初の1オクテットだけでなく、要求のすべてのオクテットがブロックの中になければならない。
ブロックの中で始まり、終端を越えて続く要求こそ、開始アドレスだけの検査が通してしまうものであり、検証はまさにそれを送る。
和を64ビットのオフセットとして計算するのは、アドレスがワイヤから来るからである。
`0xFFFFFFF0 + 0x20` は32ビットでは `0x10` になる。

許すものは1つだけである。
`obc_public_block`、SRAM 上の64オクテットで、マジック、稼働時間、メッセージカウンタを持ち、ダンプのたびに更新される。
そこには秘密が一度も書かれない。
それが本当の制御である——何が機微かを決めるのは allowlist ではなく配置であり、allowlist はその周りに引かれた線を守るだけである。

両方をビルドする。

```bash
make firmware-f02
```

これは各半分について、Makefile が周りに用意する環境（libcsp を追加モジュールとして）付きで、次の行を実行する。

```bash
west build -b nucleo_h753zi -d build-obc-f02-vuln firmware/apps/obc -- \
  -DCUBERANGE_OBC_PUS8_LENGTH_CHECK=1 -DCUBERANGE_OBC_SIGN_REPORTS=1 \
  -DCUBERANGE_OBC_PUS6_ALLOWLIST=0 -DEXTRA_CONF_FILE="$PWD/firmware/apps/obc/pus_auth.conf"
west build -b nucleo_h753zi -d build-obc-f02-hard firmware/apps/obc -- \
  -DCUBERANGE_OBC_PUS8_LENGTH_CHECK=1 -DCUBERANGE_OBC_SIGN_REPORTS=1 \
  -DCUBERANGE_OBC_PUS6_ALLOWLIST=1 -DEXTRA_CONF_FILE="$PWD/firmware/apps/obc/pus_auth.conf"
```

## 他が同一である理由

このペアは `firmware-matrix.yml` に宣言されているので、`make pair-gate` は他のすべてのペアと同じ6つの検査にこれをかける。
Kconfig が同一であること、他の `CUBERANGE_*` 変数が違わないこと、ELF が異なること、フラグがソースから参照されていること、1つの `-D` 以外はコンパイル行が同一であること、そしてその `-D` が実際に翻訳単位に届いていること。
このペアに対してはまだ走らせていない——Zephyr のツールチェーンが無いマシンで書かれたからである。
だからここに引用するゲートの出力は無く、この節はあるふりをしない。

等しく保っているもの、そしてそれぞれの理由。

- **両方とも `CUBERANGE_OBC_SIGN_REPORTS=1`。** 傍観者ではなく前提である。署名が `cr_sdls_key` を OBC にコンパイルする。それの無い硬化版は、そこに無い鍵のダンプを拒否し、効いている allowlist のように見えてしまう。検証の1番目のテストは、何かを走らせる前に、両方の ELF が鍵を持つことを確かめる。

- **両方とも `CUBERANGE_OBC_PUS8_LENGTH_CHECK=1`。** EX-F01 のオーバーフローは塞がれているので、このペアで鍵に至る道はダンプであり、硬化版の結果を「オーバーフローが問題だった」と読む者もいない。

- **両方とも `CUBERANGE_OBC_REQUIRE_PUS_AUTH=0`。** OBC はテレコマンドを一切検証しないので、要求は EX-F01 と同じく平文のフレームである。

- **ダンプハンドラは両方にある。** メモリダンプはサービスである。フラグが決めるのは、それがどのメモリを読んでよいかである。

## 設計の2つの対策と、そのどれだけがこれか

設計書の 6.5 節は、ダンプが届く鍵に対する正直な対策を2つ挙げる——(M1) Service 6 のアドレス allowlist、(M2) 鍵素材の寿命最小化と明示的ゼロ化——そして、すでにコードを実行している攻撃者はどちらでも止められないと、はっきり書くことを求めている。
その最後の部分は、次の節の最初の項目である。

**M1 はこの演習のフラグであり**、上のとおり、その全部である。

**M2 はほとんど実装されていない。**
この演習が実装しているもの:

- **ダンプハンドラは何も保持しない。** `send_dump_report` は TM 6,6 を、それが出ていく CSP バッファの中に直接組み立て、オクテットを置き場所からそのまま写す。static も、フレームローカルの中継配列も無い。ダンプ報告は EX-L02 が加えた報告ストアにも入れない。ストアは報告を逐語的に保持し、逐語的なダンプ報告は、より長く生きる2つ目の写しになるからである。これは両方のビルドにあり、違いではない。

実装していないもの:

- **鍵そのものの寿命には手を付けていない。** `cr_sdls_key` は `static const` である。image が書き込まれた瞬間から置き換えられるまでフラッシュにあり、そのアドレスはシンボルテーブルに書いてあり、この演習の何もそれを動かさない。M2 が問題にしているのはまさにその滞在であり、この演習が抜き出すのもそれである。

- **短命の写しは mbedTLS のものであって、このファームウェアのものではない。** `sign_report` は署名する報告ごとに鍵を GCM コンテキストへ展開する。mbedTLS 3.6.2——Zephyr v4.1.0 が固定している版——は、そのコンテキストと中の AES 鍵スケジュールを解放時に消去する（`mbedtls_gcm_free` と `mbedtls_aes_free`、どちらも `mbedtls_platform_zeroize` 経由）。これはライブラリのソースで読んだものであり、ここでは実測していない。このファームウェアは自分では何もせずそれに頼っており、窓を短くもしていない。展開された鍵は、毎回の署名の間ずっと存在する。

- **返したダンプは輸送路に残る。** 外へ出たダンプは、このハンドラが持たないバッファを通る。libcsp v2.1 は CSP バッファをそのままプールへ返し、消去するのは次に渡すときだけである（`CSP_BUFFER_ZERO_CLEAR`、ライブラリの CMakeLists が既定で ON にしている）。そして COMM の下りタスクは、すべての報告を static バッファでフレーム化し、フレームのオクテットは後のフレームがたまたま上書きするまで残る。どちらもソースで読んだものであり、実測していない。

## これが解決しないこと

はっきり書く。
売り込みすぎた対策は、対策が無いより悪い。

- **コード実行は、どのみち鍵を読む。** allowlist は1つのサービスの中の検査である。すでに動いているコード——そのオーバーフローが開いているビルドでの EX-F01 の攻撃者——はサービスに頼まない。`sign_report` と同じやり方で鍵を読む。MPU がフラッシュをすべてのコードに読めるよう割り当てているからである（設計書 7.4）。どんな allowlist もそれは止めないし、この射場の何も止めない。

- **1つのサービスを縛るだけである。** 要求に応じてメモリを読む他のあらゆる方法——別の保守コマンド、デバッグインタフェース、メモリ領域のファイル転送——には、それぞれの境界が要る。欠陥は「このダンプに allowlist が無かった」ことではない。鍵が image の中の何からでも読めることである。

- **1つのノードを覆うだけである。** COMM はリンクを検証するために同じ鍵を持ち（EX-S01）、それで署名か検証をするすべての image も持つ。OBC のダンプに付けた allowlist は、OBC のダンプから OBC の写しを守るだけである。

- **他のすべての OBC image は、今も任意のアドレスを返す。** ハンドラはこの射場がビルドするすべての OBC にあり、フラグの既定値は0なので、allowlist を持つ image は `build-obc-f02-hard` だけである。`SECURITY.ja.md` にそう書いてある。

- **検知について何も言わない。** 拒否は EX-F01 と同じくコンソールに出る。PUS 5 のイベントもカウンタも地上に届かないので、鍵を探してダンプサービスでアドレス空間を歩き回る者がいても、運用者に見えるものは何も残らない。

正直に言えば、これは鍵に至る道を1つ閉じ、鍵はそっくり元の場所に残す。

## 実機設計なら何をするか

鍵を image の外に置く。
アプリケーションが読み返せない保管場所へ入れる——セキュアエレメント、あるいは CPU が取り出せない鍵スロットを持つ暗号エンジン。
ただしそれを持つ部品の場合であり、この部品の CRYP はそうではないと設計書は記録している。
鍵がメモリに置かれねばならないなら、その操作のためだけに読み込み、終われば、コンパイラが取り除けない手段で消去する。
機能ごと、ノードごとに別の鍵を与え、抜き出された1つの写しが全部ではなく1つの扉だけを開けるようにする。
そして鍵を交換し（EX-S03）、抜き出された鍵の寿命を有限にする。

メモリダンプを、それが本来そうである特権操作として扱う。
認証し（EX-S02）、局ごとに認可し（EX-G02）、ビルド時に宣言した領域に限り、地上へ報告する——返したものも拒否したものも、すべてのダンプを。

CCSDS SDLS（355.0-B-2）はここでは助けにならなかったし、なりえなかった。
それが拠り所にする鍵こそ、読み出されたものだからである。
