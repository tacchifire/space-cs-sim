# EX-L01 の対策 — 前へ進んでいないフレームを拒む

*English: [mitigation.md](mitigation.md)*

## 変更点

TC 転送フレームは既に8ビットのシーケンス番号を運んでいる。
対策版の COMM は、その番号が直前に受理したものより先にあるときだけフレームを受理する。

```c
#if CUBERANGE_COMM_ANTIREPLAY
	if (have_last) {
		int8_t ahead = (int8_t)(seq - last_seq);

		if (ahead <= 0) {
			printk("COMM: REJECTED replayed frame seq=%u (last accepted %u)\n", seq, last_seq);
			return;
		}
	}
	have_last = 1;
	last_seq = seq;
#endif
```

符号付きへのキャストが肝である。
8ビットのカウンタは一周するので、`seq > last_seq` と書くと各周期の半分ですべてのフレームを拒否してしまう。

```bash
west build ... firmware/apps/comm -- -DCUBERANGE_COMM_ANTIREPLAY=1
```

EX-B01 と同じく、2つの COMM イメージはビルドフラグ1個だけで違う。
Zephyr のオプションは1つも動いていない。
`tools/config_diff_gate.py` がそれを機械的に証明する。

## これが解決しないこと

- **これは認証ではない。** 送信できる者は、より大きいシーケンス番号を持つ**新しい**指令を今も送れる。止まるのは録音であって、偽造者ではない。それ以上をやるにはフレームを鍵に結び付ける必要があり、CCSDS SDLS（355.0-B-2）がそのためにある。

- **本物のアップリンクを抑え込める攻撃者が勝つ。** 運用者を妨害してから、ずっと先のシーケンス番号で送信する。衛星はあなたのものを受理し、その周期の残りのあいだ運用者のものを拒否する。防御そのもので作られたサービス妨害である。

- **8ビットは狭い窓である。** 値は256個しかなく、リセットをまたいで保持されない。再起動すれば状態が戻り、古い録音がまた有効になる。試してほしい。COMM を電源再投入してからリプレイする。

- **守るのはリンクであって、バスではない。** EX-B01 の攻撃者はこれに一切触れられていない。

正直に言えば、これはコストを「録音して再送する」から「運用者より先に、正しい瞬間に送信する」に引き上げる。
実在する改善であり、見た目よりずっと小さい。

## 実機設計なら何をするか

仮想チャネルごとのセキュリティアソシエーションを持つ SDLS、AES-256-GCM、そして単に存在するのではなく**認証された**シーケンス番号に対するアンチリプレイ窓。
そうすればカウンタを前へ進めるのに鍵が要る。

それは Phase 2 の主題であり、設計書が現在のラボ用フレーミングを CCSDS チャネル準拠と呼ぶことを拒む理由でもある。
