# EX-G04 — 誰にも聞こえない拒否

## 状況

**何も壊れていない。**

EX-G02 の権限検査は ON で、正しく働いている。`power` を与えられていない局が指令を送り、
宇宙機はそれを拒否する。機上のコンソールにはこう出ている——
`REJECTED PUS 8 function 1 from source 67 - not authorised`。制御は設計どおりに機能している。

運用者はそのコンソールを持っていない。運用者が持っているのは下り回線であり、
下り回線の上で、その拒否はこう見える。

## 目的

**パスが開いているうちに、地上から**、次のどれが起きたのかを特定すること。

- 宇宙機が指令を拒否した
- フレームが飛行中に壊れ、CRC で捨てられた
- 上りがそもそも送信されなかった
- 宇宙機が聞いていない

そのうえで、それを可能にするには機上で何が変わらなければならないかを決めること。

## 何が動いているか

同じ 3 ノード。このペアは**両方のビルドで** EX-G02 の権限検査が ON である。
違うのは、宇宙機が拒否したことを口に出すかどうかだけである。

| ビルド | 権限検査 | 拒否を報告する |
| --- | --- | --- |
| `build-obc-g04-vuln` | する | しない |
| `build-obc-g04-hard` | する | PUS 1,2 |

## ヒント

<details>
<summary>拒否と、落ちたフレームをどう区別するのか</summary>

脆弱版では**区別できない**。そしてそれがヒントの不足ではなく、発見そのものである。
試すこと——拒否される指令を送り、次に 1 オクテット反転したフレームを送って COMM の FECF に
捨てさせる。地上が見たものを比べる。似ているのではなく、**同じ**である。
</details>

<details>
<summary>宇宙機は既に何を知っていて、言っていないのか</summary>

必要なものはすべて知っている。どの要求を拒否したか（そのパケットを手に持っている）、
そしてなぜ拒否したかを。ECSS-E-ST-70-41C のサービス 1 はまさにこのためにある。
1,2 が受理失敗報告であり、要求を**失敗したパケット自身の先頭 4 オクテット**で名指しする。
だから宇宙機は何も覚えておく必要がなく、地上は自分の記録にある指令と突き合わせられる。
</details>

<details>
<summary>ログに残して後で下ろせばよいのでは</summary>

「後で」はパスが終わった後だからである。報告の価値は、**運用者にまだリンクがあり、行動できる
うちに届く**ことにある——別の局から送り直す、表を直す、あるいは試すのをやめる。
次のコンタクトで下ろすログが伝えるのは、「あのときこうできた」である。
</details>

## 何を結論すべきか

**報告できない制御は、半分の制御である。** ここでの権限検査は正しく、テストされ、ゲートされている。
そしてそれは同時に、地上が 1 パスを誤診に費やす障害を生んだ。この 2 つは矛盾なく同じファームウェアに
同居している。**セキュリティ制御が「効いていると観測できる」かどうかは、制御自身の性質であって、
ログの話ではない。**

**沈黙は最も曖昧な信号である。** 拒否された指令も、壊れたフレームも、向いていないアンテナも、
死んだ受信機も、すべて沈黙を生む。沈黙をそのどれかに解決するものは見た目より価値があり、
ここでは安い——Request ID の 4 オクテットと、理由の 1 オクテットである。

**宇宙機に情報が不足していたことは一度もない。** 拒否したパケットも、拒否した理由も手元にあった。
**これで 3 演習連続で、修正とは「既にそこにあるものを使うこと」だった**——EX-G02 では source id が
届いて無視され、EX-G03 では仮想チャンネルが跨がれ、ここでは拒否した要求がローカル変数にあった。
3 つとも、ワイヤに新しい欄を足していない。

**そして攻撃者は沈黙から二重に利益を得る。** 一つは、誰も見ない拒否には警報を出せないこと。
もう一つは、**誤った故障を追っている運用者は、自分を見ていない**ことである。
EX-G03 の単一カウンタによるサービス妨害がまさにこれで、コンソールは「再送」と言い、
運用者は再送を探し、それを引き起こしたフレームは 30 秒前に立ち去った誰かが送ったものである。
