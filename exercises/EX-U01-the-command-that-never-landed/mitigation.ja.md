# EX-U01 — 対策

## 修正

`CUBERANGE_OBC_ACK_COMMANDS=1`。受理時に PUS 1,1 を送る。
受理したパケット自身の先頭4オクテットを Request ID として運ぶ——失敗報告が運ぶのと同じフィールドなので、
地上は自分が写しを持っている指令と突き合わせられる。

送るのは**ディスパッチの前**である。ECSS が受理をそこに置くのと同じ理由による——
受理とは「パケットが届き、ハンドラに渡せる程度に整形されている」という主張であり、
実行は別の主張である。受理されたあと拒否される指令は 1,1 と 1,2 の**両方**を生み、
**どちらも受け取らなかった運用者は、拒否だけでは決して分からないことを知る。**

## 代価

- **テレコマンド1通につき下り1パケット、永久に。** これが、ミッションが**すべてを**確認応答しない
  理由である。TC 副ヘッダの PUS 確認応答フラグは、まさに「重要な指令には受理応答を求め、
  それ以外には求めない」ためにある。この range はそのフラグを立てて**無視している**——
  簡略化であり、発見させるのではなくここに名指ししてある。
- **常設のオラクル。** 送信できる者は誰でも「そのパケットが整形されていたか」を学べる。
  テレコマンドが認証されるリンク（EX-S02）では先に MAC を偽造する必要があるので限定されるが、
  そうでないリンクでは**無料の書式チェッカ**である。

## 解決しないこと

- **受理応答そのものの遮断。** 上りを遮断できる攻撃者は 1,1 も遮断できる。
  そうなると運用者は EX-D02 と EX-L02 が置いていった場所に戻る——欠けた報告、カウンタの欠落、
  そしてそれに答える再送要求。違いは**欠けるべきものが存在するようになった**ことであり、
  改善の全部がそれである。
- **どちらの向きが失敗したか。** 指令のあとの沈黙は「指令が届かなかった」か
  「受理応答が返らなかった」を意味する。**症状が同じ別の攻撃**であり、ここでは何も分けない。
  ミッションなら報告カウンタを使う——欠落は下りが何かを食べたと言う——が、
  欠落には前後2通の報告が要り、**最初から存在しなかった受理応答は1通も残さない。**
- **実行。** 受理はパケットが整形されていたと言う。EX-F01 は、
  **整形されたパケットが誰も望まないことをする**演習まるごと1本である。
- **上りのカウンタ。** 存在しない。宇宙機には「あなたから40通聞いた」と言う手段が無く、
  地上には「41通のはずだ」と気づく手段が無い。**上りリンク版の EX-D02** であり、未実装である。

## ここから持ち帰る価値のあること

9つの演習。そしてこれは、**型が型であることをやめて、点検表になる**場所である。

EX-X01：防御は資産にではなく経路に付いている。
EX-G04：報告できない制御は、地上が使えない制御である。
EX-S01：システムで最も強い制御も、やはり経路に付いている。
EX-S02：ならば、本当に気にしている対象に束縛せよ。
EX-D01：そして、それを両方向でやったかを確かめよ。
EX-D02：そして、自分の検出が何の上に立っているかを確かめよ。
EX-L02：そして、それが敵と天候を区別できるかを確かめよ。
EX-L03：そして、それが待っている事象が実際に起きるかを確かめよ。
EX-U01：**そして、誰も何も作らなかった向きを確かめよ。**

下りリンクには演習5本分の足場が載った。**下りリンクが観測を生んだから**である。
上りリンクは何も生まず、だから何も載らなかった。そしてそれは偶然ではない——**機構である。**
**注意は証拠を追い、攻撃者は追うべき証拠が無い場所へ行く。**
