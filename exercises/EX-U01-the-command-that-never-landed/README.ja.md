# EX-U01 — 届かなかった指令

## 状況

EX-L03 は、どの制御も見ていない向きを名指しして終わった:

> **上りリンクについて何も。** スケジュールは**届いたもの**を見る。
> 何も聞こえていない宇宙機には、それを言う手段が無い。

この range が運用者のために作ったものは、**すべて下りリンクを見ている**。
カウンタの欠落、再送要求、パススケジュール、ビーコン。
代わりに**上り**を遮断すると、そのすべてが「リンクは健全」と言い続ける。
下りリンクの視点からは、実際に健全だからである。

そして宇宙機の語彙には、EX-G04 以来ずっと空いている穴がある。あの演習は
「地上が聞けない拒否は、届かなかったフレームと区別が付かない」を確立し、答えは PUS 1,2 だった。
**符号は一度も反転されなかった。** 運用者は「拒否された」と「何も無い」を区別できるが、
**「受理された」と「届かなかった」は今も区別できない。**

## 目的

指令を4通上げる。**宇宙機がそれを受け取ったかどうかを言え。**

```bash
make exercise EX=EX-U01-the-command-that-never-landed          # range の中のシェルに入る
python3 exercises/EX-U01-the-command-that-never-landed/solve.py --deny   # そのシェルのプロンプトで
```

`make exercise` は **range のネットワーク名前空間の中**のシェルに入る。ソルバはそこから走らせる。
名前空間にはループバックしか無く（SAFE_USE.md）、起動ごとに新しく作られるので、
別の端末で起動したソルバは `ConnectionRefusedError` を受け取る。

シェルではなく1コマンドだけ走らせるなら:

```bash
make exercise EX=EX-U01-the-command-that-never-landed RUN='python3 exercises/EX-U01-the-command-that-never-landed/solve.py --deny'
```

## 何が起きたか

```text
受理応答   上り遮断   送信   応答   テレメトリ   パススケジュール
あり       なし        4      4        36          ok
あり       あり        4      0        32          ok
なし       あり        4      0        30          ok
なし       なし        4      0        34          ok
```

**パススケジュールは全行で `ok` である。** ビーコンは最後まで届き、カウンタに欠落は無く、
この range が作った下り側の制御はすべて健全なリンクを報告する——**下りリンクは実際に健全だから**である。

受理応答があれば、4 対 0 が攻撃を分ける。無ければ、0 対 0 は何も分けない。

## 結論すべきこと

**1つの向きを見る制御は、1つの向きを見る。** EX-X01 の文——防御は経路に付いている——が
**5度目**に到着している。そしてここに到着したのは、テレメトリに費やした5つの演習が
**一度も「指令はどうなったのか」を問わなかった**からである。

**受理は実行ではなく、運用者には両方が別々に要る。** このビルドの PUS 1,1 は**ディスパッチの前**に
送られるので、そのあと**拒否される**指令も受理応答を受け取る。一瞬おかしく読めるが、そこが要点である——
**拒否された指令は、聞こえていた。** 「届かなかった」と「届いて、おかしくなった」は別のパスであり、
上りリンクへの攻撃なのは前者だけである。

**そして、2つの向きの扱われ方の非対称に注目すること。** 拒否は EX-G04 で作られ、
EX-D01 で認証され、EX-D02 で数えられ、EX-L02 で再要求可能になり、EX-L03 でビーコンに裏打ちされた。
**下りリンクに演習5本分の足場**である。上りリンクには何も無かった。
**上りリンクが観測を1つも生まなかったから**である——そしてそれこそが、攻撃者がそこへ行く理由である。

受理応答・その電波時間の代価・それでも言えないことは `mitigation.ja.md` にある。
