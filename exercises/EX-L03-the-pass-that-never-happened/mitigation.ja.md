# EX-L03 — 対策

## 修正は、また2箇所にある

**宇宙機側:** `CUBERANGE_OBC_BEACON=1`。タイマで出る非要求のハウスキーピング報告——
稼働時間だけを運ぶ PUS 3,25 の**部分集合**であり、ファームウェアはそれを
「サービスの実装」ではなく部分集合として書いてある。他の報告と同じ送出経路を通るので、
署名するビルドでは署名され、保存するビルドでは保存される。
**ビーコンは独自の規則を持つ特別なチャネルではない**——非要求であるだけのテレメトリであり、
**報告を取れる攻撃者はビーコンも取れる**。

**地上側:** `cuberange.gs.passes`——窓、期待、そして `ok` / `quiet` / `silent` の判定。
3つは別の所見であり、どれが人を起こす価値のあるものかを文書が言う。

**どちらの半分も単独では効かない。** スケジュールの無いビーコンは誰も数えていないテレメトリであり、
ビーコンの無いスケジュールは毎パス発火する。

## 時計の問題——ここが持ち帰る価値のある部分

レートに基づく期待——「2秒ごとにビーコン」——は**宇宙機の**時計での主張であり、
**運用者の**時計で検査される。この range は両者を異なる速さで走らせる。
実行プロファイルはエミュレート時間をホストが許す限り速く進めるので（設計 4.3、規則 G1）、
**2000 ms のビーコン周期が実時間の約 400 ms ごとに到着した**——
レートが10を予測した窓で**52通**である。

だからここの窓は `expect_at_least` を問う。**2つの時計の不一致を越えて生き残る問い**である。
実際のミッションは2つの時計を意図的に突き合わせる。それが time correlation の仕事であり、
この range は実装していない。
**失敗様態は静かで、名指しする価値がある——ある時計で較正し別の時計で評価するレート警報は、
両者の比だけ間違っており、その比は一定ではない。**

## 代価

- **電波時間と電力を、継続的に。** ビーコンは誰も聞いていなくても送信する。
  それは実際のミッションが毎回する取引であり、無料ではない。
- **敵に対する常時の信号。** ビーコンを出す宇宙機は、自分の存在を告げる宇宙機である。
  この range は RF 位置標定について何も言わず、模擬もしていない。
- **スタック。** ビーコンスレッドは署名するので、424 オクテットの `mbedtls_gcm_context` を載せる。
  既定の 1024 では**ビーコンをちょうど1通送って止まった**——W47 の形の**3度目**であり、
  だから数字は3つ目のリテラルではなく**名前付き定数**になった。

## 解決しないこと

- **なぜ静かだったのか。** 遮断も、死んだ宇宙機も、外れた予測も、別方向を向いたアンテナも、
  ここからは同じに見える。
- **部分的なパス。** 窓の大部分を遮断する攻撃者は `ok` に足るだけ残せる。
  それを捕まえる `quiet` 判定には、この range の時計が合意できないレートが要る。
- **辛抱強い攻撃者。** 20パスに1回の遮断は天候に見える——EX-L02 で1通取ることがそうだったように。
- **上りリンクについて何も。** スケジュールは**届いたもの**を見る。
  何も聞こえていない宇宙機には、それを言う手段が無い。

## ここから持ち帰る価値のあること

8つの演習、そして最後の3つは1つの議論である。

EX-D02：自分の検出が何の上に立っているかを確かめよ。（入力が偽造可能で、**開いて**失敗した。）
EX-L02：それが敵と天候を区別できるかを確かめよ。
EX-L03：**そして、それが待っている事象が実際に起きるかを確かめよ。**（入力が**存在せず**、閉じて失敗した。）

**あらゆるものに発火する検出器と、何にも発火しない検出器は、服の違う同じ欠陥である。**
そして同じ運用者が、同じ午後に、両方とも切る。
