# EX-G01 の対策 — 出自、次に形、最後に権限

*English: [mitigation.md](mitigation.md)*

## 変更点

オブジェクトを1つ差し替えるだけである。

```python
Scheduler(store, AcceptAnything(),   plugin_dir, transmit)   # 脆弱版
Scheduler(store, SignedAndBounded(), plugin_dir, transmit)   # 対策版
```

`SignedAndBounded.accept` は3つをこの順で行う。
順序自体が対策の一部である。

```python
# 1. 出自
if not hmac.compare_digest(sig, sign(doc, self._key)):
    raise ImportRejected("signature does not match the operator key")
# 2. 形。運用者が作ったと分かった文書に対してのみ
...
# 3. 権限。署名は誰が書いたかを言うだけで、何を要求してよいかは言わない
if service not in self._allowed:
    raise ImportRejected(f"service {service} may not be scheduled by import")
```

信頼する理由の無い文書のスキーマを検査するのは、攻撃者のために働くことである。
しかもスキーマエラーは、次にどのフィールドを直せばよいかを相手に教える。
だから出自が先に来る。

## 署名されていることと、許可されていることは違う

3番目が抜けやすい。
そして抜けたときに、署名付きインポート機能は署名付き何でも機能になる。

運用者の鍵は、誰がそのファイルを作ったかを証明する。
**インポート**が電源指令をスケジュールしてよいかは別の問いで、答えも別である。
この2つは絶えず混同される。

`IMPORT_ALLOWED_SERVICES` は `{3, 17}` である。
ハウスキーピングと接続試験、つまり提携先のパス計画が正当に要求するものである。
地上がレールを切るときに使う機能管理は、そこに入っていない。

`test_a_signature_alone_does_not_authorise_any_command` がまさにこれを見る。
**正当に署名された** PUS 8 の計画でも拒否される。

## ここで「1点だけ違う」が検査可能である理由

ファームウェアの演習は2つのビルドを diff して藁人形でないことを証明する。
ホスト側の Python にはその成果物が無い。
CONTRIBUTING.md の規則も Zephyr の言葉で書かれていた。

つまり、2つの版が「同一プロセス内の2つのコード経路」である演習は、「1点しか変えていない」と主張しても誰も検査できない。

そこでの類似物がこれである。
**スケジューラは1つ、ポリシーは2つ、そしてスケジューラはどちらを持っているか知ってはならない。**

`test_the_scheduler_does_not_know_which_policy_it_holds` は `schedule.py` を読み、どちらかのポリシークラスの名前が出てきたら落ちる。
ポリシーを覗けるスケジューラは、何でも変えられる。
そうなると「対策」が、受理する指令ではなく送信の仕方を静かに変えている可能性が残る。

## これが解決しないこと

はっきり書く。
売り込みすぎた対策は、対策が無いより悪い。

- **鍵はリポジトリ内の固定文字列である。** EX-B01 の `POWER_TOKEN` と同じで、帰結も同じである。地上系のファイルを読める者は計画に署名できる。コストが「ファイルを書く」から「ファイルを読んでから書く」に上がる。実在する改善であり、小さい。

- **運用者には何も及ばない。** このポリシーが統べるのはインポートである。運用者コンソールは今も何でもスケジュールでき、`test_an_operator_entry_is_not_bounded_by_the_import_policy` がそれを assert する。侵害された運用者アカウントはこの対策の脇を素通りする。それは次の演習であって、これではない。

- **2つの経路はまだディレクトリを共有している。** 署名は共有ディレクトリを生存可能にするだけで、良い設計にはしない。プラグインの出力先とインポート元を分ければ、認証で乗り越えるのではなく誤りの一分類ごと消える。しかも費用はかからない。

- **許可リストはリストでしかない。** 縛るのはサービスであって引数ではない。計画はハウスキーピングをスケジュールでき、病的なパラメータを持つハウスキーピング要求はこのポリシーを素通りする。**指令が何を言ってよいか**を縛るのは EX-A01 の主題で、ここでも解決していない。

- **送信に印が付かない。** `ScheduledCommand.origin` はエントリが `passpredict.plan.json` から来たことを記録するが、それは線上にも、宇宙機が生む記録にも届かない。事後に見れば、汚染された計画とキー入力は区別できない。

## 実機設計なら何をするか

ディレクトリを分け、プラグインの出力先が何かの入力にならないようにする。
鍵は HSM に置くか、少なくともプラグインが読めるファイルツリーの外に置く。

権限の検査は、各エントリではなく計画全体を見る場所に置く。
無線を切ってそのまま戻さない計画は、単体のエントリのどれを見ても分からない形で怪しい。

送信したすべての指令の出自を、地上系自身のログとダウンリンク可能なイベントの両方に記録する。
半年後に「これを誰が要求したのか」に答えがあるようにするためである。

そしてリンクを断ちうる指令には2名の運用者を要求する。
エントリがどう入り込んだかにかかわらず、これだけはこの攻撃を止めていた制御である。
