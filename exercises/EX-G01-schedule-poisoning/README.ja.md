# EX-G01 — 届かない宇宙機に指令を出す

*English: [README.md](README.md)*

## 状況

無線は持っていない。
バス上にもいない。
運用者アカウントも無く、宇宙機に触れることは一度もない。

持っているのは、地上系のプラグインディレクトリにファイルを書ける権限だけである。
ミッション用のツールを書く者、そのツールを侵害した者、あるいは単にそれを導入させた者の位置である。
パス予測、接近解析、ペイロードのスケジューラ。
地上系はそうしたツールをいくつも統合し、どれも出力をどこかに書く。

その同じディレクトリから、地上系はスケジュールファイルを取り込む。

## 目的

何も送信せずに衛星を沈黙させる。
成功条件は `EPS: COMM rail OFF (commanded)` が出ること。
そのとき指令を送ったのは、あなたが書いた計画にもとづく運用者自身の地上局である。

## 動いているもの

```
   plugins/ ────────► 地上系 ──► COMM.usart2 ──CSP/CAN──► OBC ──► EPS
   ここにいる       取り込んで送信      宇宙機側の制御はすべて対策版
```

EPS は EX-B01 のトークンを要求する。
COMM は EX-L01 のリプレイを拒む。
OBC は EX-F01 の長さ検査で PUS 8 のコピーを縛る。
3つとも、この攻撃の最中に完璧に働く。

## 実行

```bash
make firmware-g01
python3 exercises/EX-G01-schedule-poisoning/solve.py --dir /tmp/cuberange/gs-plugins
make verify EX=EX-G01-schedule-poisoning
```

## ヒント

<details><summary>ヒント1 — 信頼境界がどこにあるべきだったか</summary>

`src/cuberange/gs/schedule.py` の `Scheduler.import_pending` を読む。
そのうえで、読み込んでいるディレクトリについて2つ問う。
他に誰がそこへ書くのか。
そこで見つかったファイルについて何が検査されるのか。
</details>

<details><summary>ヒント2 — 計画の形</summary>

`src/cuberange/gs/import_policy.py` に2つのポリシーが並んでいる。
脆弱な地上系が使うのは `AcceptAnything` である。
それが読むフィールドが、あなたのファイルに必要なフィールドである。

スケジューラは PUS のサービスとサブタイプを送信する。
つまり地上局が送れるものは何でも、計画から要求できる。
</details>

<details><summary>ヒント3 — どの指令か</summary>

運用者が COMM のレールを切るときに使うものである。
PUS 8,1、機能1、状態0。

偽造しているのではない。
本物を送ってくれと地上系に頼んでいる。
</details>

## 何を結論すべきか

**すべての制御が働いた。** それがこの演習のすべてである。
EPS は指令を認証し、指令は本物だった。
OBC はコピーを縛り、コピーは収まっていた。
COMM はリプレイを検査し、リプレイではなかった。
フレームのチェックサムが正しいのは、地上局が計算したからである。

宇宙機側の対策を4演習ぶん積み上げ、そのすべてが機能していて、それでも無線は落ちた。
どれ一つとして**何を送るかを誰が決めたか**についての制御ではなかったからである。

**認可はメッセージの属性ではない。**
EX-B01 は「送信者は秘密を知っているか」を問うた。
EX-L01 は「これを前に見たか」を問うた。
EX-A01 は「ハードウェアにこれができるか」を問うた。
EX-F01 は「これは収まるか」を問うた。

この4つすべてを満たす指令が、それでも誰も出す資格の無かった指令でありうる。
その問いを立てられる場所は、計画が組み立てられるところしか無い。

**1つのディレクトリ、2つの信頼水準。**
欠陥は、抽象的にインポータが不注意だということではない。
同じパスが、サードパーティ製ツールの出力先であり、同時にコマンド経路の入力源でもあることである。

これはごく平凡で、極めてよくある形である。
そしてこの演習が、設計書の初期案のような同語反復にならない理由でもある。
「DB に書ける者が DB を書ける」は何も教えない。
それが破棄された記録は設計書の16節にある。

**送信された指令には出自の印が付かない。**
`ScheduledCommand.origin` はエントリがどこから来たかを記録するが、それを線上に載せるものは何も無い。
宇宙機から見ても、後からダウンリンクを読む者から見ても、汚染された計画と運用者のキー入力は同じ出来事である。

Willbold らの *Space Odyssey*（IEEE S&P 2023）はファームウェアの論文であり、この演習はその対象外の部分にあたる。
実際の事案の多くは地上系から始まり、そこはシステムの中で最も調べられていない半分である。

## そして直す

[mitigation.ja.md](mitigation.ja.md) を見てほしい。
検証はエミュレートされた宇宙機を相手に、3方向すべてを assert する。

| テスト | 何を assert するか |
| --- | --- |
| `test_the_attack_works_against_the_permissive_importer` | プラグインのファイルが送信になり、レールが落ち、しかも EPS は何も拒否していない |
| `test_the_mitigation_refuses_the_plugin_s_file` | インポータが拒否を記録し、レールは落ちない |
| `test_the_mitigation_still_transmits_the_operator_s_own_plan` | 署名済みで許可された計画は今も取り込まれ、送信される |

1つ目はレールが落ちることに加えて、EPS のコンソールに `REJECTED` が**無い**ことも assert する。
これが無いと、EPS が指令を拒んだ実行と、汚染された計画が honored された実行が同じに見える。
この演習は後者だけである。

`tests/pytest/test_schedule_policy.py` にさらに14件ある。
反・藁人形の証明もそこにある。
スケジューラはどちらのポリシークラスの名前も出してはならず、「2つの版はポリシーオブジェクトだけが違う」ことを約束ではなく検査にしている。
