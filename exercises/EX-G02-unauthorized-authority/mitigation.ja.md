# EX-G02 の対策 — 最初からそこにあった識別子を読む

## 変更点

`CUBERANGE_OBC_REQUIRE_AUTHORITY=1` と、表が 1 つ。

```c
static const struct pus8_authority AUTHORITY_TABLE[] = {
	{ GROUND_PRIMARY_ID, FUNC_SET_COMM_RAIL },
	/* GROUND_BACKUP_ID は意図的に載せていない。 */
};

#if CUBERANGE_OBC_REQUIRE_AUTHORITY
	if (!source_may_perform(source_id, function_id)) {
		printk("OBC: REJECTED PUS 8 function %u from source %u - not authorised\n", ...);
		return;
	}
#endif
```

`source_id` は既に `handle_space_packet` のローカル変数だった。すべてのテレコマンドから取り出し、
コンソールに出力していた。対策がしたのは、それを 1 つ下の関数へ渡して**見る**ことだけである。
新しい欄も、新しいプロトコルも、鍵も要らない。

検査は引数コピーの**前**に走る。要求に従うかどうかの判断は、その要求のデータをローカルバッファに
入れ終わってからするものではない。

## 脆弱版に表が存在しない理由

`#if` は検査だけでなく表そのものを囲んでいる。コンパイルされているのに一度も参照されない表は、
別の——そしてより不正直な——欠陥である。認可表を書いておいて呼び忘れる人はいない。
ここで起きたのは、**誰も書かなかった**ことである。

## 「1 つだけ違う」がここで検査可能な理由

`firmware-matrix.yml` がこのペアを宣言し、`tools/config_diff_gate.py` が、2 つのイメージが
`CUBERANGE_OBC_REQUIRE_AUTHORITY` だけで違うことを証明する——Kconfig シンボル 836 個が同一、
全翻訳単位のコマンドラインが同一、ELF は相違。

1 つのアプリケーションに 2 つのペアが乗ることになった。EX-F01 は自分の両半で
`CUBERANGE_OBC_REQUIRE_AUTHORITY` を等しく保ち、こちらは自分の両半で
`CUBERANGE_OBC_PUS8_LENGTH_CHECK` を等しく保つ。だからゲートは両方について
「ちょうど 1 つが違う」と言える。

## 署名と許可は違う。認証とも違う

3 つが混同されやすいので、分けて書く。

- **認証**が答えるのは「これは本当に副局か」である。ここでは何もそれを行っていない。
  source id は、リンクに到達した攻撃者が自由に書ける平文の欄である。
- **認可**が答えるのは「副局はこれをしてよいか」である。この対策が足したのはこれである。
- **完全性**が答えるのは「送られたとおりに届いたか」である。FECF が事故を捕まえ、
  EX-L01 の再送防止が再送を捕まえる。

この対策は真ん中の 1 つだけである。局が自分の権限を超えることは止める。
より大きな権限を持つ局だと名乗ることは止めない。

## これが解決しないこと

対策を過大に売るのは、対策が無いより悪い。はっきり書く。

- **source id は認証されていない。** リンク上の攻撃者が `0x0042` と書けば、この表にとっては
  主局である。これは費用を「自分のコンソールを使う」から「リンクに到達して 1 オクテット書き換える」
  へ上げる。実質的であり、かつ小さい。リンクが主題なのは EX-L01 であり、その対策とこれを
  組み合わせて初めて正直な構成になる。そしてそれでも共有秘密は平文でコミットされている。
- **表は静的でコンパイル時に固定される。** 実際の権限は変わる。サイトが落ちる、パスが引き継がれる、
  局が廃止される。この表を変えるのはファームウェアのビルドとアップロードであり、
  パスの最中に誰もやらない。つまり切迫した場面での現実的な答えは「迂回する」になる。
- **覆っているのは PUS 8 だけである。** サービス 17 は検査対象外で、ここではそれが正しい——
  副局は ping してよい。しかし、次に追加される特権サービスがこの表に行を持たないまま入ることを
  設計上何も止めていない。検査はサービスごとのオプトインであって既定拒否ではなく、
  実機設計が望むのは既定拒否である。
- **拒否は printk である。** OBC コンソール——エミュレーションではファイル、実機では UART——には
  届くが、地上には届かない。設定を誤った表に締め出されている運用者と、拒否されている攻撃者は、
  下り回線から見て同一である。つまりどちらも見えない。次に作るべきものはこれであり、
  EX-G01 の「送信に印が付かない」が反対側から現れたものである。
- **正規局が何を言ってよいかは何も縛っていない。** 主局は電源線を入れてよい。食の最中に切ることも
  できる。**指令が何を要求してよいか**を縛るのは EX-A01 の主題であり、ここでは解決していない。

## 実機設計なら何をするか

権限はパケット内の欄ではなく、**認証された経路**に結び付けられる。識別子はフレームに署名した鍵を
持つ者から来て、表はそれを鍵にする。CCSDS SDLS（355.0-B-2）がその土台となるフレームレベルの
セキュリティアソシエーションを与え、NASA CryptoLib——このリポジトリに既に golden ベクタの
オラクルとして入っている——がそれを実装している。

表そのものはアップロード可能でバージョン付きにし、宇宙機は自分が持つより古いバージョンを拒否する。
そうすれば引き継ぎにファームウェアのビルドが要らず、古い表の再送で廃止済みの局が復活することもない。

そして拒否はテレメトリになる。サービス、サブタイプ、送信元を名指しした PUS 1 の受理失敗報告として
下ろす。締め出されているのか攻撃されているのかを、パスが開いているうちに地上から区別できるように。
