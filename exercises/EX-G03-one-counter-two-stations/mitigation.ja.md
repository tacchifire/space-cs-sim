# EX-G03 の対策 — カウンタはリンクではなくチャンネルのもの

## 変更点

`CUBERANGE_COMM_ANTIREPLAY_PER_VC=1`、そして変数ではなく表。

```c
static uint8_t last_seq_vc[64];
static uint8_t have_vc[64];
uint8_t vc = cr_tc_frame_vcid(frame, len);

if (have_vc[vc]) {
	int8_t ahead = (int8_t)(seq - last_seq_vc[vc]);
	if (ahead <= 0) { reject; }
}
```

エントリが 64 なのは VCID 欄が 6 ビットだからである。追い出し処理を持たない固定表にしたのは、
方針を持つキャッシュとは**攻撃者が駆動できる方針**だからである。128 バイト。

再送防止はこのペアの両半で ON である。違うのはカウンタが**どこに属するか**で、
だから `firmware-matrix.yml` はこのペアを `CUBERANGE_COMM_ANTIREPLAY` ではなく
`CUBERANGE_COMM_ANTIREPLAY_PER_VC` で宣言している。

## 必要なものは既にフレームに載っていた

新しいのは `cr_tc_frame_vcid` であって、欄ではない。CCSDS 232.0-B-4 の 4.1.2.5 は、
すべての TC 転送フレームのオクテット 2 に 6 ビットの仮想チャンネル識別子を置いている。
デコーダはオクテット 4 から連番を読み出しながら、その欄を跨いでいた。
そして COP-1 はその連番を**仮想チャンネルごと**に維持する（FARM 状態は VC 単位）。
つまり規格は、この演習が問う質問に既に答えていた。

これは EX-G02 と同じ形である。あちらでは PUS の source id が届き、記録され、何も決めていなかった。
**2 回続けて、修正とは「既にワイヤに載っている欄を読むこと」だった。**

## これが解決しないこと

対策を過大に売るのは、対策が無いより悪い。はっきり書く。

- **攻撃者がチャンネルを選ぶ。** `--vcid 0` を渡せば、緩和版に対しても攻撃はそのまま効く。
  VCID は平文の欄であり、誰がそこで送信してよいかを認証するものは何も無い。
  費用が上がるのは「何でも送る」から「**運用者自身のチャンネルで送る**」までで、
  その番号は運用者自身のトラフィックから読める。実質的であり、かつ小さい。
  EX-L01 と EX-G02 と同じ終わり方であり、理由も同じ——どのフレームも認証されていない。
- **カウンタは 64 個あり、攻撃者は全部埋められる。** 表は固定長で各エントリは独立なので枯渇はしないが、
  64 チャンネル全部で送信する攻撃者は 64 全部を止める。チャンネルごとのアクセス制御は無い。
  その土台になる認証が無いからである。
- **窓は依然 8 ビットである。** 十分に先のフレームは一周して後ろになる（演習のヒントのとおり）。
  そして再起動で表は消え、古い録音がまた有効になる。どちらも EX-L01 の限界であり、ここでは変わらない。
- **状態を検知しない。** コンソールは今もチャンネル番号つきで `REJECTED replayed frame` と言うだけである。
  見たことのないチャンネルが現れたことも、あるチャンネルが現れて以来もう一方が拒否され続けていることも、
  宇宙機は気づかない。**「VC 1 が 14:02 に出現し、以後 VC 0 が拒否され続けている」**と言える防御があれば、
  この演習は 5 分の診断になっていた。そしてそれは修正そのものより価値がある。

## 実機設計なら何をするか

連番検査を COP-1 に似せるのではなく、COP-1 そのものを実装する。スライディング窓を持つ FARM-1、
再送の状態機械、そして受信側が期待する連番を地上へ返す CLCW テレメトリ。
この対策に最も目立って欠けているのが最後の部分である——宇宙機が何を期待しているかを地上が知る手段が無いので、
締め出された運用者はリセット無しに再同期できない。

その下に認証を置く。CCSDS SDLS（355.0-B-2）がフレームを鍵に結び付け、
それによって初めて「この仮想チャンネルで誰が送信してよいか」が答えのある問いになる。
このレンジの演習はすべてここで終わる。そしてそれ自体が、この演習集の主題である。
