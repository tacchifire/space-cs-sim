# EX-S01 — 対策

## 既にある修正

`CUBERANGE_OBC_CROSSLINK_ORIGIN=1`——EX-X01 のもの、そのまま。そして今も効く:

```
OBC: REJECTED a packet claiming source 66 that arrived from node 13
OBC: PUS 1,2 acceptance failure reported to source 66 (code 4)
```

認証ではなくトポロジ検査である。攻撃者が選べない「どこから入ったか」を、攻撃者が書く
「誰が送ったか」の代わりに見る。それが何を買い、何を買わないかは EX-X01 の文書が詳しく書いており、
アップリンクに SDLS を入れたことでその内容は1つも変わらなかった。

**そこが噛みしめる価値のある点である。** 覆われていない経路の弱い制御は、覆われた経路に強い制御が
入った**後でもまったく同じだけ必要**である。変わるのは、誰かがそれを覚えている確率だけである。

## 正しい修正と、その代価

SDLS をクロスリンクにも広げる。僚機トラフィック用の2本目の Security Association、独自の鍵、
独自の再送カウンタ、そして何かを覆う MAC——そして「何かを覆う」がそのまま作業量である。
クロスリンクが運ぶのはトランスファフレームではなく CSP パケットで、
**CCSDS 355.0-B-2 は CSP パケットについて何も言っていない**。定義されたセキュリティヘッダが無い。

したがって次のどれかになる:

- **クロスリンク上のトランスファフレームに SDLS を載せる。** 僚機トラフィックを TC フレームで
  包み、同じコードを走らせる。誠実であり、クロスリンクを2本目の宇宙リンクにする——
  クロスサポート用の無線とは、だいたいそういうものである。
- **CSP 層で認証する。** libcsp には HMAC オプション（`CSP_USE_HMAC`）がある。この range は
  コンパイル対象外にしており、CryptoLib 自身の TC 経路も未ビルド時は HMAC フラグ付きフレームを
  落とす。同じ問いに対する別プロトコルの答えである。
- **アプリケーション層で認証する。** PUS パケット自身が MAC を持つ。すると
  **どのリンクから来たかが問題にならなくなる**——上の2つが持っていない性質である。

この演習に実際に答えるのは3番目で、そしていちばん作業量が多い。
ここでは未実装であり、**ほのめかすのではなく名指しして**ある。

## この修正が解決しないこと

- **鍵を持った僚機。** 上のどれもコンステレーションに共有秘密を与え、侵害された宇宙機はそれを
  持っている。`keys.py` は書き下された1本の鍵がこの range にとって誠実な形である理由を長く述べて
  いるが、効く文は同じである——**固定の共有秘密は、証明するものではなく持っているものである**。
- **自機の COMM。** origin 検査が COMM を信じるのは、どこかで何かを信じなければならないからで、
  クロスリンク上の MAC も COMM が検証する。
- **認証された局が何を要求してよいか。** EX-G02 はこれら全部に対して無傷である。
  認証は「誰か」に答え、認可は「何を」に答え、SDLS は完全に前者の側にある。
  暗号を配備して止まった range には、EX-G02 がそのまま残る。
- **再送ウィンドウ。** SA が1本ということはカウンタが1本ということで、EX-G03 の問題が再発する——
  1本の SA に2局が乗れば、1本の仮想チャネルに2局が乗ったときと同じように締め出し合う。
  SDLS にはその修正を置く場所がある（再送状態は SA のものなので、2局には SA を2本）。
  この range はまだ置いていない。**発見させるのではなく書いてある。**

## ここから持ち帰る価値のあること

3つの演習が、3つの方向から同じ文に着く。

EX-X01：防御は資産にではなく経路に付いている。
EX-G04：報告できない制御は、地上が使えない制御である。
EX-S01：**システムで最も強い制御も、やはり経路に付いている**。そしてその強さが、それを忘れやすくする。

アップリンクの MAC は、見た目より弱い答えだったのではない。**広告どおりの強さで、覆っている
フレームの範囲においてちょうどそのとおりに強い。** そしてそのあと書き下される文が、それより短い。
