# EX-A01 — 気づかれずに衛星を回す

*English: [README.md](README.md)*

## 状況

あなたは再び衛星の CAN バス上にいる。
EX-B01 と同じ位置である。

前回から変わったことが一つある。
EPS が正しいトークンを持たない電源指令を拒むようになったので、無線を沈黙させた手口はもう効かない。

それでよい。
あの制御は最初から問題の全体ではなかった。

ADCS は磁気トルカを所有する。
その指令はトルクをミリニュートンメートルで、符号付き16ビット整数として運ぶ。
つまりワイヤ形式は -32768 から +32767 までを許す。
コイルが出せるのは 20 である。

## 目的

衛星を生かしたまま、応答させたまま、発電できなくする。
成功条件は ADCS のコンソールに `ADCS: TUMBLING - panels off sun` が出ること。
その間ずっと、地上局にはテレメトリが届き続けている。

## 動いているもの

```
地上局 --TCP--> COMM.usart2 --CSP/CAN--> OBC
                  COMM  OBC  EPS  ADCS  attacker  ------  CAN ハブ1本
                                  |
                       gpioPortD.6 = タンブル指示器
```

ここでの EPS は EX-B01 の**対策版**である。
衛星ノードは3つではなく4つになった。

## 実行

```bash
make firmware-a01
make exercise EX=EX-A01-adcs-tumble      # シナリオを起動したままにする
python3 exercises/EX-A01-adcs-tumble/solve.py     # 模範解答
make verify EX=EX-A01-adcs-tumble
```

## ヒント

<details><summary>ヒント1 — どこを見るか</summary>

ADCS は CSP ポート 12 で待ち受ける。
指令は8オクテットで、opcode、軸、16ビットのトルク、予備4バイトである。
`firmware/apps/adcs/src/main.c` を読み、コイルが実際に出せる数値を探す。
そのうえで、脆弱版がトルクを積分する前に何を検査しているかを見る。
</details>

<details><summary>ヒント2 — バスにフレームを載せる</summary>

EX-B01 と同じインジェクタ、同じポート、同じ行プロトコル `"<hex can id> <hex data>"` である。
`src/cuberange/proto/csp.py` がパケットを組み立てて断片化する。

静かに何も起きない2つの間違いも同じである。
拡張29ビットではなく標準11ビットのフレームを送ること。
そして、エミュレーションが停止している間に注入すること。
</details>

<details><summary>ヒント3 — 何を見張るか</summary>

テレメトリではない。
衛星は最後まで応答し続ける。
そこが要点である。

`/tmp/cuberange/adcs.uart` を見るか、検証コードと同じように指示器のピンを読む。
ADCS マシンの `gpioPortD` ODR、`0x58020C14` のビット6である。
</details>

## 何を結論すべきか

2つある。
持ち帰る価値があるのは2つ目である。

**欠けていた制御は認証ではなかった。**
EX-B01 の対策はここでも設計どおりに働く。
EPS はあなたの偽造した電源指令を拒む。
それでいてこの攻撃には何の効き目もない。
ADCS の指令はもっともらしくないどころではないからである。
書式は正しく、宛先も正しく、プロトコルが合法だと言うトルクを要求している。
同じ値を実際の運用者が送っても受理される。
**誰が**要求しているかを知っても、**何を**要求されたかが実行可能かは分からない。

**この故障は静かで、静かなほうが悪い。**
EX-B01 は沈黙で終わる。
テレメトリが止まり、運用者は1パス以内に異常を知る。
こちらは、すべてのサブシステムが正常を報告したまま終わる。
無線は動く。
OBC は応答する。
ハウスキーピングは予定どおり届く。
運用者に届く最初の証拠は、数時間後の電池のトレンドであり、その時点ではまだ誰もそれを見る理由を持っていない。
そのころ衛星は何周回も太陽を外している。

すべての演習が沈黙で終わる演習環境は、運用者に「応答している」を「健全である」と読む癖をつける。
これはその反例である。
だから検証は、攻撃が通った**あとも衛星が生きている**ことを assert する。

Willbold らは実在の衛星ファームウェアでこの形を繰り返し報告している（*Space Odyssey*, IEEE S&P 2023）。
構造と出自は検証するのに、要求された値がハードウェアに実行可能かは検証しないコマンドハンドラである。

## そして直す

[mitigation.ja.md](mitigation.ja.md) を見てほしい。
検証は3方向すべてを assert する。

| テスト | 何を assert するか |
| --- | --- |
| `test_attack_succeeds_against_the_vulnerable_adcs` | 偽造トルクが衛星を回し、しかも応答し続ける |
| `test_mitigation_rejects_the_out_of_authority_torque` | 同じ指令が拒まれ、姿勢が保たれる |
| `test_the_mitigation_does_not_break_legitimate_slews` | 権限内のトルクは今も実行される |

3番目は前の2つと同じだけ重要である。
すべての姿勢指令を拒む ADCS は、対策された ADCS ではなく死んだ ADCS である。
