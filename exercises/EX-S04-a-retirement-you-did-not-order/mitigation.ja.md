# EX-S04 — すべての Security Association に所有者を、そして誰も帰属できない退役

## 対策ビルドがすること

このペアは、両方の半分が三つの Security Association すべて、`owner` フィールド、そして `STOP_SA`
ディレクティブのハンドラを持っている。**テレコマンドによる SA 管理は差分ではない——それは機能で
ある。** 差分は認可チェック一つである。

```c
struct cr_sdls_sa {
        uint16_t spi;
        const uint8_t *key;
        uint8_t owner;            /* この SA が属する当事者 */
        bool operational;
};

static struct cr_sdls_sa sa_table[] = {              /* 可変になった：EX-S04 は実行時に退役させる */
        { CR_SDLS_SPI,         cr_sdls_key,         CR_SDLS_OWNER_OPERATOR, /* ... */ },
        { CR_SDLS_SPI_ROTATED, cr_sdls_key_rotated, CR_SDLS_OWNER_OPERATOR, true },
        { CR_SDLS_SPI_PARTNER, cr_sdls_key_partner, CR_SDLS_OWNER_PARTNER,  true },
};
```

`STOP_SA` ディレクティブは予約された制御用バーチャルチャネルに、他のフレームと同様に認証されて届く
——だから COMM がそれを読む時点で、送信者の*身元*はすでに証明されている：彼らはフレーム化に使った
SA の鍵を保持している。`CUBERANGE_COMM_SA_MGMT_AUTHORITY=1` が加える唯一のチェックは、認証では
答えられない問いを問う：

```c
#if CUBERANGE_COMM_SA_MGMT_AUTHORITY
        if (sa_table[requester].owner != sa_table[target].owner) {
                /* 拒否。そして無線が名指すのは対象ではなく REQUESTER である */
                return;
        }
#endif
        sa_table[target].operational = false;
```

その `#if` 一つがペアの差分のすべてである。`SA_DEACTIVATION` は**両方**の半分で `0` に固定されて
いるので、すべての SA は operational で起動し、退役は回線上で起きる。連携局の SA もハンドラも両方の
半分に入っているので、ペアゲートは `CUBERANGE_*` フラグの変化をちょうど一つ見て、それ以外は何も
見ない——これが「機能を消しただけ」の対策を防ぐ。

拒否は**対象**（SPI 9）ではなく**要求者**（SPI 11）を名指す。対象を名指せば運用者は自分の
association を見に行くことになるが、それこそ*変わっていない*ものだ。事案は「誰かが越権した」で
あり、報告に値するのは越権した当事者である。

## ディレクティブと、正直な空白

`STOP_SA` は三オクテット——ディレクティブ種別と対象 SPI——で、制御 VC 7 に載る。**外側**の認証
フレームは `tools/oracles/sdls_oracle.c` が既に NASA CryptoLib と突き合わせているものなので、その
レイアウトはオラクルで裏付けられている。**内側**のディレクティブにはこのリポジトリにまだ相当する
オラクルがない：CCSDS 355.1 拡張手続きには CryptoLib の実装があるが、それをゴールデンオラクルとして
配線するのはそれ自体が一つのプロジェクトである。だから内側 PDU は `test_c_matches_python.py` が
C と Python を突き合わせて検査し——両パーサが同じ短すぎる PDU を拒否することを含めて——`ASSURANCE.md`
に空白として明記される。自作パーサ二つが一致することは証明ではない。まさにそれが、この空白を
飾り立てず書き留める理由である。

## これが解決しないこと

**帰属（Attribution）。** これが発見であり、次の演習である。地上から見れば、攻撃（行 1）と正規の退役
（行 3）は*同じ観測*だ：SPI 9 が応答しなくなる。認証は*誰がディレクティブをフレーム化したか*に答え、
認可は*してよかったか*に答えた——そして**どちらもダウンリンクに乗らない**。誰が SA を退役させたかの
記録は COMM のコンソール（`by SPI 11` か `by SPI 10` か）だけで、それは機上を離れない。これは EX-G04
と EX-U03 の問題——効いているのに効いていると聞こえない制御——が SA 管理にやって来たものだ。SPI 9 が
暗くなっているのを見つけた運用者は、自分がやったのか敵がやったのかを、見えるものからは言えない。

**可用性。** 本演習は同じコマンドの*破壊的な*方向を意図的に守っていない。`STOP_SA` が**最後の**運用
SA を退役させ、機上をまったく指令不能にすることをここでは何も止めない。無効化より有効化を先に順序
付けもしないので、依存する SA より先に届いたディレクティブは足場が未定義になる。どちらも現実であり、
どちらも認可そのものではなくその隣人であり、畳み込めばペアの差分が一つの考えより大きくなってしまう。
次の演習が正直に攻撃できるよう、ここに名を挙げておく。

**所有者が誰であるか。** `owner` は表にコンパイルされたタグであって、ミッションが管理する身元では
ない。現実の SA 管理は、この range が行わない鍵管理を通じて権限を管理主体に束ねる——`keys.py` が
鍵そのものの周りに引くのと同じ境界だ。生き残る教訓は制御の*形*であって、鍵管理を作ったという主張
ではない。

## ここから持ち帰るべきこと

EX-S03：鍵を退役させ、入れてくれと頼むことでドアが閉じたかを確かめる。
EX-S04：**そしてドアを閉じよと頼んだそのフレームが、送信者に送る権利のあるものだったかを確かめる。**

本演習より前のあらゆる制御は、フレームが*正当か*——整形式で、新しく、正しく署名されているか——を
問うた。本演習は、送信者が*要求した効果への権利を持っていたか*を問う。それは別の問いであり、別の
答えを持つ：連携局のフレームは完全に正当で、完全に無認可である。**有効な署名は鍵についての言明で
あって、その保持者の権利についての言明ではない**——そして認証された当事者が自分の所有しないものに
作用できるようになった瞬間、修正はより良い署名ではない。それは所有者である。
