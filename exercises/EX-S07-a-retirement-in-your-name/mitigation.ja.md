# EX-S07 — 地上の台帳、そしてログには問えない問い

## 対策ビルドがすること

対策*ビルド*は無い。両ランとも EX-S06 の hardened COMM（`CUBERANGE_COMM_SA_MGMT_HISTORY` on）を積み、
宇宙機はどちらでも同一の SA 管理ログを出す。これは EX-G01 と同じ**地上側**のペアである——違うのは地上局の
1フィールドだ。

```python
# GroundStation, EX-S07
self.sa_directives_sent = []          # この局が組んだ全 STOP_SA、(退役させた SPI, 組んだ元の SPI)
self.owned_spis = frozenset(...)      # この局の所有者が持つ SA——または None、「判定できない」

@property
def unexplained_sa_retirements(self):
    if self.owned_spis is None:
        return None                   # [] ではない——「判定できない」と「異常なし」は別の答え
    unmatched = Counter(self.sa_directives_sent)
    out = []
    for entry in self.sa_retire_log:          # (退役 SPI, 退役させた SPI)、ビーコンから
        if entry[1] not in self.owned_spis:
            continue                  # 連携局の SA——EX-S05/S06 が帰属する。この問いではない
        if unmatched[entry] > 0:
            unmatched[entry] -= 1     # 自分が送ったディレクティブ1件が、ログ1項を説明する
        else:
            out.append(entry)         # 自分の名前で、送った記録が無い
    return out
```

照合する局が対策のすべてである。自分が送った STOP_SA ディレクティブの台帳を保ち、**退役させた元の** SPI が
自分のものであるログ項ごとに、送った覚えのあるディレクティブと1件ずつ相殺する。残るのは、*運用者の名前で、
運用者が命じていない*退役——運用者が持つ鍵が、運用者でない誰かに使われた徴候だ。**ログ順のマルチセット**で
ある：STOP_SA(9) を1回送ると `(9, 10)` 項を1つだけ説明するので、鍵のコピーが生む2つ目は吸収されない。

**自分が所有する SA を名指す項だけを判定する。** 連携局が SPI 11 で SPI 9 を退役させるのは EX-S05・EX-S06 が
すでにダウンリンクに載せた帰属であり、それを運用者に帰すのはあらゆる退役に泣く検出器になる。この検出器は
ただ一つの問いに答える——*私が持つ鍵が、私でない誰かに使われたか*。

**ディレクティブはテレコマンドではなく、カウンタがそれを証す。** `send_sa_stop` は `commands_sent` ではなく
`sa_directives_sent` に記録する——COMM がディレクティブを処理し OBC は見ないので、EX-U02 の
`unexplained_commands` はそれで動かないからだ。テレコマンドとして数えると、運用者自身のローテーションが
`unexplained_commands = −1`（失われた指令、EX-U01 の症状、誤った事件を指す）と読めた。機能テストでいまそれが
`0` と測られている。

## これが解決しないこと

**検出はするが、防止はしない。** ここでは何も退役を止めない——EX-S04 の所有者検査は、その自分のビルド上で
これを*認可する*。SPI 10 鍵のコピーは、本物の鍵とまったく同じに `owner` の等号を満たすからだ（演習が測る：
連携局の SPI 11 は拒否され、コピーの SPI 10 は拒否されず、SPI 9 は暗転する）。台帳は、自分の名前での退役が
送っていないものだと運用者が事後に気づくことを可能にするだけだ。ここが求める防止は**鍵管理**——保有者に
束ねられた SA、危殆化の疑いでの鍵ローテーション——であり、この range はそれを名指して作らない。EX-U02 が、
盗まれた鍵はここのどの制御も覆わない前提だと最初に述べた。EX-S07 はそれを解かず、その帰結をダウンリンクから
読む。

**検出には照合するログが要り、そのログは EX-S06 のもの——有界で、報告された場合に限る。** SA 管理ログを
報告しないビルド（EX-S05 のスナップショット、または報告 off の COMM）は、照合する局に何も残さない：
`unexplained_sa_retirements` は空リストを返し、クリーンなランと同じ答えになる。入力が存在しないからだ。run 5 が
EX-S04 のビルドでこれを測る。そしてログが*報告される*場合もそれは EX-S06 の有界リングなので、最も古い端から
こぼれた退役は台帳がもう照合できない——EX-S06 が名指した有界ログの限界を、ここが受け継ぐ。

**鍵を持つ全員が照合しなければ、ギャップは移動するだけだ。** 台帳は局ごとである。SPI 10 を共有する運用者の
2局（EX-G03 の二局問題）は各自の送ったものしか知らないので、一方が送った退役はもう一方では未説明と読まれる。
完全な検出器は、鍵を持つ全局を覆う台帳を要する——EX-G03 の単一リプレイカウンタと同じ形の、鍵管理での1層上だ。

## ここから持ち帰るもの

EX-S06：誰がどの SA を退役させたかの系列を保て。最新状態のスナップショットは上書きされるから。
EX-S07：**そしてそれを自分の「何をしたか」の記録と照合せよ。帰属は鍵を名指し、あなたの鍵のコピーは、
自分が何を送ったか覚えている者以外の全員にとってあなたなのだから。**

認証は鍵が検証されたことを伝える。その鍵があなたが使ってよいものだったかは伝えられない——それはフレームの
性質ではなく、宇宙機側のどの制御も取り戻せない。宇宙機は鍵しか握らなかったからだ。答えは地上に、運用者自身の
「何をしたか」の記録にある。EX-G01 が、宇宙機側の制御には供給できない権限を見つけたのと同じ場所だ。盗まれた
退役の証人は衛星上には無い。運用者が命じた退役について保つ台帳、それである。
